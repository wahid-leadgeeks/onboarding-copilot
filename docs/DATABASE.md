# Database mode (PostgreSQL)

The app normally reads and writes the Google Sheet (ADR-0001). Database mode is optional: when
`DATABASE_URL` is set, the app uses a PostgreSQL working copy instead. This page covers how that
database is created, migrated, seeded and filled from local JSON files, and how to bring an older
database (created by the previous seed script) under managed migrations.

> **Agents never connect to the remote database.** Every command on this page that targets the
> remote (shared or hosted) database is run by a person. Automated agents only use a throwaway
> local cluster, and always pass that local URL explicitly.

## Modes and environment

| Variable | Effect |
|---|---|
| `DATABASE_URL` | When it starts with `postgres://` or `postgresql://`, the app runs in database mode (`isDbConfigured()` in `lib/db/index.ts`). Unset: Sheets mode. |
| `AUTH_DISABLED=true` | Skips the Google login (`middleware.ts`). Intended for a local database-mode setup only. |
| `TEST_DATABASE_URL` | Throwaway local database for integration tests. Never point it at a real database. |

The schema lives in `lib/db/schema.ts`. Migrations live in `drizzle/` (SQL files plus
`drizzle/meta/_journal.json`) and are generated by drizzle-kit. `drizzle.config.ts` does not load
`.env.local`; `db:generate` and `db:check` need no connection. (drizzle-kit itself auto-loads
`<cwd>/.env`, never `.env.local`.)

### SSL rule

All scripts and the app use `resolveSslOption(url)` from `lib/db/ssl.ts`:

- URL contains `sslmode=disable` → no SSL.
- URL contains `localhost` or `127.0.0.1` → no SSL.
- Anything else → `ssl: 'require'`.

### Where scripts get the URL (URL-source rule)

Every DB script (`sync:diary`, `sync:schedule`, `db:migrate`, `db:seed`, `db:inspect`) resolves the
URL in this order and prints it (password masked) before connecting:

1. the positional argument: `pnpm db:migrate postgres://...` → `source: positional`
2. the `DATABASE_URL` environment variable → `source: env`
3. `DATABASE_URL` in `.env.local` → `source: .env.local` (read only when 1 and 2 are absent)

```
Target: postgres://user:****@host:5432/db (source: .env.local)
```

`.env.local` is read relative to the **current working directory**, not the repository. Because the
repository's `.env.local` holds the remote URL, running `pnpm sync:*` or `pnpm db:inspect` from the
repo root without a positional URL or `DATABASE_URL` reads from (dry-runs against) the **remote**.
Check the printed `Target:` line.

Writes are refused when the URL came from `.env.local`: `sync:* --apply`, `db:migrate` and
`db:seed` exit 1 before connecting unless you pass `--allow-env-file`. Pass the URL explicitly
(positional or `DATABASE_URL=... pnpm ...`) instead whenever you can. Dry runs and `db:inspect`
may use `.env.local`.

Run `pnpm db:seed` (and any script that imports `lib/` modules using `@/` aliases) from the
repository root.

## Commands

| Command | Connects? | Writes? |
|---|---|---|
| `pnpm db:generate --name <name>` | no | writes `drizzle/` files |
| `pnpm db:check` | no | no |
| `pnpm db:migrate [url] [--allow-env-file]` | yes | applies pending migrations |
| `pnpm db:seed [url] [--allow-env-file] [--allow-non-empty]` | yes | inserts catalog rows |
| `pnpm db:inspect [url]` | yes, read-only session | no |
| `pnpm -s db:baseline-sql` | **never** | no, prints SQL to stdout |
| `pnpm sync:diary` / `pnpm sync:schedule` | yes | only with `--apply` |

`db:inspect` accepts every sync flag but ignores them all.

## Fresh database

```sh
pnpm db:migrate "$URL"   # creates all tables from drizzle/
pnpm db:seed "$URL"      # fills the catalog tables
```

`db:migrate` prints the target, then `Migration rows: N (applied now: K)`. Running it again applies
nothing (`applied now: 0`).

## Existing remote database created by the old seed script (user-run only)

Older databases were created by the `CREATE TABLE IF NOT EXISTS` statements that used to live in
`scripts/seed-db.ts`, and patched by the old schedule sync script. They hold the same nine tables
as `drizzle/0000_baseline.sql`, with these differences:

- **`activities.materials_link`**: the old seed DDL did not create it, and `activities.activity_count`
  was `integer NOT NULL`. The old schedule sync script added them at run time with
  `ALTER TABLE activities ADD COLUMN IF NOT EXISTS materials_link text DEFAULT ''` and
  `ALTER TABLE activities ALTER COLUMN activity_count DROP NOT NULL`. A database that never ran that
  script lacks the column and still has `NOT NULL`.
- **Unique constraint names**: the old DDL declared `UNIQUE` inline, so PostgreSQL named the
  constraints `<table>_<column>_key` (`diary_entries_row_number_key`,
  `feedback_entries_session_id_key`, `monthly_reviews_month_key`). drizzle names them
  `<table>_<column>_unique` (`diary_entries_row_number_unique`, and so on). The constraints are
  equivalent; only the names differ. They are renamed so that later drizzle migrations that refer to
  the constraint by name work on both old and fresh databases.

`db:migrate` cannot run on such a database directly: it would try to `CREATE TABLE "activities"`
again and fail. Instead you record the baseline migration as already applied, after making the
schema match it. Every step below is idempotent and safe to re-run.

Run these steps yourself, in order. Set `URL` in your shell first (for example `read -rs URL`) so
the password does not land in your shell history.

1. **Inspect.** `pnpm db:inspect "$URL"` (read-only session). Save the output outside the repo. The constraints section excludes NOT NULL entries (PG18 lists them in `pg_constraint`) because the columns section already covers nullability.
2. **Compare with the baseline.** Compare the columns and constraints with `drizzle/0000_baseline.sql`
   (or with `db:inspect` of a fresh local database after `db:migrate`). Expect only the differences
   listed above. Anything else: stop and resolve it first.
3. **If `drizzle.__drizzle_migrations` exists with rows, stop and inspect.** Something already
   migrated or baselined this database. Compare its rows with the `hash`/`created_at` values printed
   by `pnpm -s db:baseline-sql` and find out what wrote them before going further. (An empty table can
   be left behind by an earlier failed `db:migrate`; see the note below. That case is fine.)
4. **Patch `activities` if step 2 showed it is needed.** Both statements are idempotent:

   ```sql
   ALTER TABLE activities ADD COLUMN IF NOT EXISTS materials_link text DEFAULT '';
   ALTER TABLE activities ALTER COLUMN activity_count DROP NOT NULL;
   ```

5. **Rename the old unique constraints.** Each rename only runs when the old name exists:

   ```sql
   DO $$ BEGIN IF EXISTS (SELECT 1 FROM pg_constraint WHERE conname='diary_entries_row_number_key' AND conrelid='diary_entries'::regclass) THEN ALTER TABLE diary_entries RENAME CONSTRAINT diary_entries_row_number_key TO diary_entries_row_number_unique; END IF; END $$;
   DO $$ BEGIN IF EXISTS (SELECT 1 FROM pg_constraint WHERE conname='feedback_entries_session_id_key' AND conrelid='feedback_entries'::regclass) THEN ALTER TABLE feedback_entries RENAME CONSTRAINT feedback_entries_session_id_key TO feedback_entries_session_id_unique; END IF; END $$;
   DO $$ BEGIN IF EXISTS (SELECT 1 FROM pg_constraint WHERE conname='monthly_reviews_month_key' AND conrelid='monthly_reviews'::regclass) THEN ALTER TABLE monthly_reviews RENAME CONSTRAINT monthly_reviews_month_key TO monthly_reviews_month_unique; END IF; END $$;
   ```

   Run steps 4 and 5 with `psql "$URL" -v ON_ERROR_STOP=1`.
6. **Record the baseline.** `pnpm -s db:baseline-sql | psql "$URL" -v ON_ERROR_STOP=1`

   The script never connects; it prints one transaction that creates `drizzle.__drizzle_migrations`
   if needed and inserts one row per journal entry (hash = sha256 of the `.sql` file, `created_at` =
   the journal `when`) unless a row with that `created_at` or newer already exists. Running it twice
   leaves exactly one row. (`pnpm -s` writes its `$ tsx ...` echo to stderr, so only SQL reaches
   psql. If any statement fails, the transaction is rolled back.)
7. **Confirm nothing is pending.** `pnpm db:migrate "$URL"` must report `applied now: 0`.
8. **Inspect again.** `pnpm db:inspect "$URL"`: the columns and constraints now match a fresh
   database, and `drizzle.__drizzle_migrations` has one row.

Notes:

- **Column order**: on an old database `materials_link` is the last column of `activities`; on a
  fresh one it sits before `notes`. This is harmless: drizzle and the app address columns by name,
  and `db:inspect` sorts columns by name.
- **drizzle's bookkeeping is outside the migration transaction**: `migrate()` runs
  `CREATE SCHEMA IF NOT EXISTS drizzle` and `CREATE TABLE IF NOT EXISTS drizzle.__drizzle_migrations`
  before it opens the transaction that applies migrations. A failed `db:migrate` can therefore leave
  an empty `drizzle` schema and table behind. That is harmless; the next run reuses them.
- drizzle applies a migration only when the newest row's `created_at` is smaller than the journal
  `when` of that migration (drizzle-orm `pg-core/dialect.js`). The hash is recorded but not compared.

## Making schema changes

1. Edit `lib/db/schema.ts`.
2. `pnpm db:generate --name <short_name>` and review the new SQL in `drizzle/`. Never edit an
   applied migration; add a new one.
3. `pnpm db:check`.
4. Apply to a local throwaway database (`pnpm db:migrate postgres://postgres@127.0.0.1:<port>/<db>`)
   and test.
5. Commit the schema change and the `drizzle/` files together. The remote is migrated by a person
   with `pnpm db:migrate "$URL"`.

### Rollback policy

Migrations are **forward-only**. To undo a change, write a new migration.

- The inverse of the baseline (dropping all tables and the `drizzle` schema) is only for disposable
  local or test databases. Never run it against the remote.
- Every future migration documents its manual rollback SQL (and any data it cannot restore) in a
  comment at the top of its `.sql` file or in the commit message.

## Sync scripts: JSON files → database

`pnpm sync:diary` fills `diary_topics` + `diary_entries`; `pnpm sync:schedule` fills `activities`.

```
pnpm sync:diary    [url] [--file path] [--apply] [--prune] [--force] [--force-prune] [--allow-env-file]
pnpm sync:schedule [url] [--file path] [--apply] [--prune] [--force] [--allow-env-file]
```

### Files

- Defaults: `data/private/diary.json` and `data/private/schedule.json`, shaped
  `{ "version": 1, "rows": [...] }`. `data/private/` is gitignored because it holds personal data.
- Fake fixtures for trying things out: `data/examples/*.example.json` (rows 190-192).
- **Back up `data/private/` outside the repository.** `git clean -X` (or `-x`) deletes ignored
  files, including these.

### Flags

| Flag | Meaning |
|---|---|
| (none) | **Dry run.** Reads in a read-only transaction, prints the plan, writes nothing. |
| `--apply` | Write the plan in one transaction, after locking the compared rows. |
| `--prune` | List (dry run) or delete (with `--apply`) database rows that are missing from the file. |
| `--force` | Overwrite protected-field conflicts (see below). Nothing else. |
| `--force-prune` | Diary only: also prune `diary_entries` that contain learned/notes text. Accepted by `sync:schedule` but a documented no-op there. |
| `--allow-env-file` | Permit `--apply` when the URL came from `.env.local`. |
| `--file <path>` | Use another rows file. |

At most one positional argument (the URL). A leading `--` is ignored. Unknown flags are an error.

### Rules

- Every row is validated first. Rejected rows are listed with their position in the file and their
  `rowNumber`; any rejection aborts the run before connecting.
- Rows are matched by stable keys: schedule by `id` (`sched-row-<n>`), diary topics by `id`
  (`row-<n>`) and diary entries by `row_number`.
- **Protected working fields** are fields you also edit in the app: schedule `duration_minutes`,
  `start_time`, `end_time`, `progress`, `materials_link`, `notes`; diary entries `learned`, `notes`.
  If the database value is non-empty and differs from the file, that is a **conflict**, and the run
  aborts with zero writes unless `--force`. Comparison treats `''` and `NULL` as equal and ignores
  CRLF vs LF and surrounding whitespace.
- Only inserted or changed rows are written; unchanged rows keep their `updated_at`.
- **Prune safety**: prune is refused when the file has 0 valid rows. Activities referenced by
  `session_logs.activity_id` are never deleted (a blocker, not forceable: handle those session logs
  first). Diary entries with text are skipped unless `--force-prune`; the dry run lists them.
- No DDL. Run `pnpm db:migrate` first.

### Exit codes

| Exit | When |
|---|---|
| 0 | Dry run with nothing that would block an apply, or a successful `--apply`. |
| 1 | Rejected rows, blockers, conflicts without `--force`, a refused `.env.local` write, a missing URL, or any error. **A dry run also exits 1 when the same `--apply` would abort**, so you can gate an apply on it. |

### Output contains your data

Dry-run and apply output prints database and file values (each up to 80 characters) to the
console, for example `UPDATE row-12: learned: "..." -> "..."`. Never paste it into public issues
or pull requests; this repository is public.

## Seed safety

`pnpm db:seed` only inserts catalog rows; it contains no DDL and assumes `pnpm db:migrate` has run.

- It refuses to run when `activities` already has rows, unless `--allow-non-empty`. The check and
  all inserts run in one transaction, so a refusal or failure writes nothing.
- Inserts use `ON CONFLICT DO NOTHING`, so existing rows (including your edits) are never
  overwritten.
- It follows the URL-source rule: a URL from `.env.local` is refused without `--allow-env-file`.
